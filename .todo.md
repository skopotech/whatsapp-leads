CI now calls `scripts/test/run.sh` (protected) instead of `make test`, and lints workflows with actionlint.
- [ ] **P2 · Branch protection as a committed ruleset.** (Was P1. Same protection `make protect-main` already sets; adopt it when the harness guard needs an owner bypass.) `.github/rulesets/main.json` imported by
      `make protect-main` through the rulesets API, instead of the legacy protection endpoint. It is
      reviewable, versioned, and supports bypass actors for the harness override. Check plan
      limits: rulesets on private repos need a paid plan.
- [ ] **P3 · Acceptance criteria IDs proven by tests.** (Was P1. High per-ticket cost — IDs, tags, PR section, tooling per test runner — and it proves a test exists and passes, not that it is good; in the worker run, weak tests were caught by `/conformance-review`, not by tags. Revisit for large teams, compliance or audit contexts, or many agents merging in parallel.) Each criterion gets an ID
      (`<ticket>-AC<n>`); the test that proves it carries the ID as a tag; `verify.sh full` checks
      that every criterion that needs a test has a passing tagged test (from the test runner's JSON
      report), and that the PR body has an "Acceptance" section pointing to the file. Turns
      "the reviewer thinks it's covered" into a machine check. Ref: `scripts/check-acceptance.cjs`.
- [ ] **P2 · Frozen acceptance criteria.** After the plan is approved, a PreToolUse hook denies
      edits to that ticket's acceptance file, so the agent cannot change the test target to make
      it pass. Unfreezing is a human decision. Ref: `.claude/hooks/freeze-acceptance.sh`.
- [ ] **P2 · Plan commit before code** (`plan-ticket`). The agent writes the plan (decisions,
      files and interfaces, data changes, acceptance file) and stops; a human approves it on a
      generated review page; the approved plan is a commit; implementation starts in a fresh
      session from it. The conformance review then checks the diff against the plan commit.
- [ ] **P2 · Contract drift view.** For projects with an API: snapshot `openapi.json` and the DB
      schema in git, and show the reviewer what changed in contract and schema since the plan.
      Ref: `scripts/contract-view.cjs`.
- [ ] **P2 · Push gate.** A PreToolUse hook on `git push` that runs `scripts/secret-scan.sh` and
      refuses the push unless `verify.sh full` passed on the current HEAD. Today secrets are
      caught in CI, after the push; this catches them before they leave the machine.
- [ ] **P3 · Full-verification lock.** `verify.sh full` stops after the third identical failure in
      a row and only the user unlocks it; subagents may not run `full`. Prevents an agent burning
      tokens in a retry loop.
- [ ] **P3 · CI diagnostics.** Upload test reports as artifacts and print service logs on
      failure (stack-specific, belongs in each project's CI).
- [ ] **P3 · Path-scoped rules** (`.claude/rules/*.md` with `paths:`) for stack conventions, e.g.
      NestJS controller rules loaded only when editing controllers. Claude Code only: keep the
      portable version in `CODING_STANDARDS.md` and `apps/<app>/AGENTS.md`.
- [ ] **P3 · Docker-first development.** Every command runs inside the Compose services, never on
      the host. Good for teams with mixed machines; document it as a pattern in
      `docs/monorepo.md`, not as a template default.

## 4. Professional design that doesn't look AI-generated

- [ ] **P1 · Start from references, not from the model's taste.** Each product picks 2–3 reference
      products in its category and records why in `docs/design-system.md`. The grill asks for them.
- [ ] **P1 · A written "don't" list** against common AI tells, enforced by `design-review`:
  - purple-to-blue gradients, glassmorphism and glow as decoration;
  - emoji as icons; mixed icon sets;
  - every section a centered hero with three feature cards;
  - many accent colors; color as the only signal of state;
  - inconsistent radii and shadows on everything;
  - generic copy ("Unlock the power of…", "Seamless", "Revolutionize"), lorem ipsum;
  - stock 3D illustrations; fake testimonials and logos.
- [ ] **P1 · Constraints that make it look designed:** one accent color; a two-weight type scale
      with negative tracking on titles; a strict spacing scale; one radius grammar (controls,
      containers, actions); shadow only on overlays; real copy written for the user's task; empty,
      loading, error and partial states designed, not left to defaults.
- [ ] **P2 · Real content.** Design with real data (actual property listings, real names and
      prices), never placeholders: layout problems only show with real lengths.
- [ ] **P2 · Accessibility as part of quality.** WCAG AA contrast (checked from tokens), focus ring
      on every interactive element, 44×44px touch targets, keyboard paths, reduced motion.
- [ ] **P2 · Evaluate design skills before writing one.** `make skills-find Q=design` and the
      official marketplace (for example a frontend-design skill); compare with and without on the
      showcase page before adopting.
- [ ] **P3 · Human design pass.** For launch-critical screens, a designer (or the owner) reviews the
      Figma frames before implementation; the agent implements, it doesn't art-direct.

## 5. Security checklist to put an application online

Turn into a `docs/security.md` owner document plus checks in `verify.sh`/CI as each project needs
them. The grill's "Every feature" questions already ask about auth, data and secrets.

**Already in the template:** secret scanning in CI (`scripts/secret-scan.sh`), `.env` reads denied
to agents, force push and agent merges denied, least-privilege CI token (`contents: read`),
Dependabot for GitHub Actions, `/security-review` in the workflow, `REVIEW.md` safety item.

- [ ] **P1 · Threat model per feature.** Who can call it, with what data, what goes wrong; recorded
      in the spec. A short checklist in `docs/context.md` Engineering questions (extend it).
- [ ] **P1 · Dependency scanning for the stack.** Dependabot (or Renovate) for npm/go/pip, plus
      `npm audit` / `govulncheck` / `pip-audit` in `verify.sh full`.
- [ ] **P1 · SAST.** GitHub CodeQL (free on public repos) or Semgrep in CI.
- [ ] **P1 · Secrets management.** Runtime secrets in the host's secret store or GitHub
      environments, never in the repo or images; rotation procedure written down; push protection
      enabled on GitHub (Settings → Code security).
- [ ] **P1 · Authentication and sessions.** Proven library, never hand-rolled crypto; password
      hashing with argon2id/bcrypt; secure, HttpOnly, SameSite cookies; session expiry and
      rotation; MFA for admins; brute-force protection and rate limiting on auth endpoints.
- [ ] **P1 · Authorization.** Deny by default; check ownership on every object access (IDOR);
      tests for "user A cannot read user B's data".
- [ ] **P1 · Input and output.** Validate every input at the boundary (schema, size, type);
      parameterized queries; output encoding; file upload limits, type checks and storage outside
      the web root.
- [ ] **P1 · Transport and headers.** HTTPS only with HSTS; CSP; `X-Content-Type-Options`,
      `Referrer-Policy`, `Permissions-Policy`, frame-ancestors; CORS allowlist, never `*` with
      credentials.
- [ ] **P1 · Personal data (GDPR/LGPD).** Data inventory, legal basis, retention, deletion and
      export on request, privacy policy and terms, consent for cookies that need it, no personal
      data in logs.
- [ ] **P2 · Logging, monitoring and alerts.** Structured logs without secrets or PII; alerts on
      error rate and auth failures; uptime monitoring; audit log for admin actions.
- [ ] **P2 · Backups and recovery.** Automated, encrypted, off-site backups; a tested restore;
      written RPO/RTO.
- [ ] **P2 · Infrastructure.** Least-privilege service accounts and API tokens; WAF/CDN in front
      (e.g. Cloudflare), DDoS protection; separate staging and production; infrastructure changes
      reviewed like code.
- [ ] **P2 · Supply chain.** Lockfiles committed; pinned base images and actions (Dependabot keeps
      them current); SBOM for releases; no `curl | bash` in builds; MCP servers pinned.
- [ ] **P2 · Incident response.** Who is called, how to rotate keys, how to inform users; a
      `SECURITY.md` with a contact for vulnerability reports.
- [ ] **P3 · Pre-launch review.** `/security-review` over the whole codebase, an OWASP ASVS level 1
      pass, and an external pentest for apps handling payments or sensitive data.
- [ ] **P3 · Skills.** Evaluate maintained security skills (`make skills-find Q=security`) and a
      `threat-model` skill, project scope only.

## 7. Insights from prisma/skills and github/spec-kit (reviewed 2026-10-16)

From **prisma/skills** (vendor-maintained skills, Agent Skills format):

- [ ] **P1 (fintech) · Consent checkpoint for destructive operations.** Prisma itself detects agent
      environments and refuses `migrate reset` / `db push --force-reset` until it receives the
      user's exact consent text. Generalize it: a `.github/dangerous-commands` list (DB resets,
      migrations against shared databases, `terraform destroy`, `kubectl delete`, production
      deploys, `cast send`, `forge script --broadcast`) enforced by a PreToolUse hook that denies
      them to agents unless the user explicitly consents in that turn. Protected by the harness guard.
- [ ] **P2 · Vendor skills first, pinned to the library version.** Prefer skills maintained by the
      tool's vendor (prisma/skills, vercel-labs) over community ones; they carry
      `metadata.version` matching the library. Add a check that warns when a vendor skill's version
      drifts from the installed library major version.
- [ ] **P2 · Routing between sibling skills in descriptions** ("for Prisma Compute deploys use
      `prisma-compute`"), so the agent picks the right one; apply to company skills.
- [ ] **P3 · Skill lifecycle.** When a company skill is renamed, keep a deprecated alias skill that
      points to the new name for one release.
- [ ] **P3 · Rule catalogs with impact levels** (CRITICAL/HIGH/MEDIUM, one reference file per
      rule) for company coding standards, loaded on demand instead of growing `CODING_STANDARDS.md`.

From **github/spec-kit** (spec-driven development toolkit):

- [ ] **P1 (fintech) · Invariants as a constitution.** `docs/invariants.md` with the non-negotiable
      rules (money in integer minor units, no floats on monetary paths, idempotency of every
      externally triggered operation, tenant isolation, audit trail, double-entry balance).
      Versioned, protected by the harness guard, changed only through an ADR. `REVIEW.md` treats any
      violation as High automatically. Cotejo already has these in its instructions file.
- [ ] **P2 · Pre-implementation spec review** (spec-kit's `/analyze`): a read-only, manual skill
      that checks spec ↔ tickets ↔ ADRs ↔ invariants before `/implement`: vague adjectives without
      a measure ("fast", "secure", "scalable"), unresolved placeholders, requirements with no
      ticket, tickets referring to things the spec never defines.
- [ ] **P2 · Explicit ambiguity markers.** `/to-spec` writes `[NEEDS CLARIFICATION: …]` instead of
      guessing; `layout.test.sh` (or verify) fails when a `ready-for-agent` ticket still has one.
- [ ] **P3 · Requirement checklists as "unit tests for requirements"** per domain (payments,
      authentication, accessibility), evolving the Engineering questions in `docs/context.md`.
- [ ] **P3 · Feature-level convergence** after the last ticket: compare the code with the whole
      spec and open tickets for what is still unbuilt.
- Not adopted: spec-kit's full specify → plan → tasks pipeline. It overlaps with grill → spec →
  tickets and, as Matt Pocock argues, owning the whole process makes problems in it harder to fix.

## 8. Company-wide standard (fintech / web3 / distributed systems)

- [ ] **P1 · Three distribution layers.**
  1. *This template*: the repository skeleton (owner documents, harness, CI), per project.
  2. *An internal plugin marketplace* for company skills and hooks (invariants review, threat
     model, payment patterns, dangerous-commands guard): versioned, namespaced, updated in one place.
  3. *Managed settings* (MDM, `/Library/Application Support/ClaudeCode/managed-settings.json`,
     `/etc/claude-code/managed-settings.json`, or server-managed) for what no project may relax:
     `disableBypassPermissionsMode`, `allowManagedPermissionRulesOnly`, `allowManagedHooksOnly`,
     `allowManagedMcpServersOnly` with `allowedMcpServers`/`deniedMcpServers`,
     `strictKnownMarketplaces`, `availableModels`, `forceLoginOrgUUID`, OTEL telemetry.
- [ ] **P1 · Template updates reach existing projects: `make template-update`.** Today a project
      copies the harness once and drifts. Groundwork done in v0.1.0: `TEMPLATE_VERSION` +
      `CHANGELOG.md` in the template, and `.template-version` written into every project by
      `init.sh`. **Decision (2026-10-17): `make template-update`**, a three-way diff applied on a
      branch, chosen over copier/cruft (a migration of the whole template) and over moving the
      harness into the plugin (Claude Code only, loses the agent-neutral core). Real need: PR #3
      (mise.toml stub + doctor warning) must reach skopotech/whatsapp-leads, and mayraruas-worker
      predates the guard, the secret scan and macOS CI.
      Plan (one spec, about 4 tickets):
      1. **Baseline without release bureaucracy.** `.template-version` gains `synced: <sha>` (the
         template commit last applied). The first update falls back to the `v<version>` tag (v0.1.0
         is on GitHub). No new tags or versions are needed for updates to work.
      2. **The script** (`scripts/template-update.sh`, called by `make template-update`): add the
         `template` remote from the `template:` line if missing, fetch, create the branch
         `template-update-<short-sha>`, and apply `git diff <base> template/main -- <paths>` with
         `git apply -3`. Then write the new `synced:` line, print the CHANGELOG entries in the
         range, and list the conflicts. It never commits, pushes or opens the PR; the human
         reviews, and the harness guard asks for `harness-change-approved` as usual.
      3. **What it touches, and what not.** In: `.claude/`, `.github/`, `scripts/` (minus
         `init.sh`/`new-project.sh`), the template's own skills (`conformance-review`), `Makefile`,
         `docs/` owned by the template, `REVIEW.md`. Out, with a "review by hand" note: files
         `init.sh` rewrote or removed (README, AGENTS.md, LICENSE, CHANGELOG, CODEOWNERS), the
         Makefile's template-only block, upstream-vendored skills (those go through
         `make skills-update`), and every vendored skill in plugin mode. `scripts/verify.sh` and
         `CODING_STANDARDS.md` are customized per project, so they conflict by design and are
         listed rather than skipped.
      4. **Tests** (`scripts/test/template-update.test.sh`): a fake template repo with two commits
         and a project created from the first. Cases: clean update; conflict on a customized
         `verify.sh` (conflict markers, nothing lost); plugin mode skips the skills; the
         template-only Makefile block is left alone; re-running with nothing new is a no-op; a
         dirty working tree refuses to start. Then validate on whatsapp-leads (small diff) and
         mayraruas-worker (large diff, the real stress test).
      **Cost (estimate):** about 150–250 lines of bash plus about 150 of tests; 2–3 agent sessions
      (spec + tickets, implementation with TDD, validation on the two projects), roughly one day
      of focused work. Ongoing cost: every template change has to apply cleanly as a diff (the
      test catches it), and each update costs the project one reviewed PR with the harness label,
      which is the point. Main risk: conflicts on customized files; the mitigation is that the
      harness keeps project-specific settings in the files meant for them (`verify.sh`,
      `mise.toml`, `harness-protected`), not scattered.
- [ ] **P1 · Segregation of duties.** Agents never hold production credentials, signing keys or
      deploy rights; production deploys only from CI with a protected environment and human
      approval; CODEOWNERS with two reviewers on money, auth and key-management paths; signed
      commits; agent attribution trailers (`Co-Authored-By`) kept for the audit trail.
- [ ] **P1 · Web3 pipeline, separate from app code.** Foundry unit + invariant fuzz tests, Slither
      in CI, formal verification for critical contracts, an external audit before mainnet,
      testnet first, upgrades behind multisig + timelock, deployer keys in HSM/MPC. Agents may
      write and test contracts; they never sign or broadcast (dangerous-commands list).
- [ ] **P2 · Distributed-systems questions in the grill.** Add to the Engineering questions:
      partial failure, duplicate and out-of-order delivery, idempotency keys, retries with backoff
      and timeouts, outbox/saga for cross-service consistency, clock skew, backpressure,
      reconciliation jobs, SLOs and the runbook for each alert.
- [ ] **P2 · Test strategy for money.** Property-based tests on ledger and money arithmetic
      (balances always sum to zero, no rounding drift), injected clocks, fuzzing of every external
      parser, contract tests between services, failure injection for retries and timeouts,
      expand/contract migrations.
- [ ] **P2 · AI governance.** Approved models per data classification; no customer data or PII in
      prompts; MCP servers allowlisted and pinned; content from outside the company (issues,
      tickets, web pages) treated as untrusted input (prompt injection); spend limits and OTEL
      metrics per team.
- [ ] **P2 · Measure the standard.** DORA metrics (lead time, change failure rate, MTTR) plus
      harness signals: Stop-hook blocks, conformance findings by severity, retros applied. Review
      the standard quarterly; remove rules that stopped catching anything.

      expand; a short onboarding (`/team-onboarding` can draft it from real sessions).

## 10. Web3 specialization: Solidity and Rust (EVM, Solana, Stellar)

Goal: the rigor of the large web3 companies (auditors, protocol teams), as a harness agents cannot
weaken. Researched 2026-10-16.

**What already exists (knowledge, not harness)**
- Trail of Bits: a skills marketplace (`trailofbits/skills`, 35+ plugins; `building-secure-contracts`
  with vulnerability scanners for Solana, Substrate, Cosmos, Cairo, TON, Algorand, plus
  audit-prep-assistant, code-maturity-assessor, token-integration-analyzer; also
  differential-review, property-based-testing, mutation-testing, static-analysis,
  supply-chain-risk-auditor, spec-to-code-compliance, rust-review). Plus `claude-code-config`
  (per-user settings: denies reading `~/.ssh`, cloud credentials and **wallet data** — MetaMask,
  Phantom, Solflare, Electrum, Exodus) and `claude-code-devcontainer` (isolation to run agents
  with fewer prompts). ToB warns their AI checks are incomplete and never replace manual review.
- OpenZeppelin: Contracts MCP and `@openzeppelin/contracts-cli` (Solidity, Cairo, Stellar
  generators) and OpenZeppelin Skills built on them.
- Solana Foundation: `solana-foundation/solana-dev-skill` (version compatibility matrix, testing
  pyramid with LiteSVM and Mollusk, security checklist, Codama clients, Token-2022).
- Stellar: `stellar/stellar-dev-skill` (Soroban, assets/SAC, RPC, wallets, ZK), the Raven MCP
  server, `llms.txt`.
- Foundry: prompting guidance only (review AI code, unit + fuzz + revert tests); no agent harness.
- Not found: a repository template that enforces audit-grade rigor end to end in CI for agents.
  That is the gap.

**Decision (2026-10-16): a fork with planned synchronization**, not packs inside the base. Web3 is
wide enough to deserve its own template, and teams that don't build web3 keep a lean base.

- [ ] **P1 · Fork setup.** New repository (for example `web3-project-template`) forked from this one,
      with this template as the `upstream` remote. It has its own `TEMPLATE_VERSION` and changelog,
      and records the base version it tracks (for example `base: 0.1.0` in a `BASE_VERSION` file).
- [ ] **P1 · Keep merges conflict-free.** Web3 content lives in its own files and folders
      (`docs/web3/`, `docs/invariants.md`, chain packs under `stacks/evm|solana|stellar/`, extra
      lines appended to `.github/harness-protected`, web3 skills in `.agents/skills/`). Edits to base
      files are kept minimal and listed in the fork's README, so each upstream merge touches few lines.
- [ ] **P1 · Sync cadence.** After every base release: `git fetch upstream --tags`, merge the tag
      (`git merge v0.X.Y`), run the self-tests on Linux and macOS, bump `BASE_VERSION`, release the
      fork. A CI job in the fork can warn when upstream has a newer tag than `BASE_VERSION`.
- [ ] **P2 · Improvements flow both ways.** A generic fix found while working on the fork goes to the
      base first (PR upstream), then comes back through the next sync, never patched only in the fork.
- Chain packs live **inside the fork** (`init.sh --stack evm|solana|stellar`), EVM first.

- [ ] **P1 · Keys never reach the agent.** Deny reads of `~/.foundry/keystores/**`,
      `~/.config/solana/**` (keypairs), `~/.config/stellar/**`, wallet application data, and
      `.env` files with `PRIVATE_KEY`; enforce at user/managed level, not only per project.
- [ ] **P1 · Signing and broadcasting are human-only.** Dangerous-commands guard (section 7) with
      `forge script … --broadcast`, `cast send`, `cast wallet`, any `--private-key`,
      `solana program deploy`, `anchor deploy`, `solana transfer`, `stellar contract deploy`,
      `stellar contract invoke … --send`. Agents simulate (`--dry-run`, local anvil/validator,
      testnet forks); people sign.
- [ ] **P1 · `verify.sh` per chain, as the definition of done.**
  - EVM: `forge fmt --check`, `forge build --deny-warnings`, unit + fuzz + invariant tests with
    fixed run counts, coverage threshold on contracts, `forge snapshot --check` (gas regression),
    Slither (and Aderyn) with a baseline, solhint.
  - Solana: `cargo fmt --check`, `cargo clippy -D warnings`, `anchor build`, LiteSVM/Mollusk unit
    tests, fuzzing (Trident), `cargo audit` / `cargo deny`.
  - Stellar: `cargo fmt`, `clippy`, `stellar contract build`, Soroban unit tests with the test
    environment, `cargo-fuzz`, `cargo audit`.
- [ ] **P1 · Invariants constitution for contracts** (`docs/invariants.md`): access control on
      every state-changing function, checks-effects-interactions, rounding direction always in
      the protocol's favor, no unbounded loops over user-controlled data, oracle freshness and
      manipulation bounds, upgrade storage layout, total supply and accounting identities. Each
      invariant has a matching invariant/property test; violations are High in `REVIEW.md`.
- [ ] **P1 · Pinned toolchain.** `solc` version and optimizer in `foundry.toml`,
      `rust-toolchain.toml`, Anchor/Solana CLI versions from the compatibility matrix, libraries
      pinned by commit; the agent never upgrades a compiler outside a dedicated ticket.
- [ ] **P2 · Testing pyramid for contracts.** Unit → fuzz → stateful invariant → fork tests against
      mainnet state → formal verification for critical code (Halmos/Certora for EVM, Kani for
      Rust) → mutation testing to prove the tests catch bugs.
- [ ] **P2 · Audit readiness as a deliverable.** Threat model, NatSpec, scope file, known-issues
      list, ToB `audit-prep-assistant` and `code-maturity-assessor` before an audit;
      `differential-review` on every change after it.
- [ ] **P2 · Audited code is frozen.** Paths covered by an audit go into
      `.github/harness-protected` (or a sibling list) so any change needs an explicit
      re-audit approval label. The harness guard already provides the mechanism.
- [ ] **P2 · Deployment ceremony in CI only.** Reproducible builds, source verification
      (Sourcify/Etherscan, `solana-verify`, reproducible wasm), deployment manifests and an
      address registry in the repo, Safe/Squads multisig, timelocks on upgrades, post-deploy
      verification script, pause/guardian runbook.
- [ ] **P2 · Vendor the official knowledge, pinned.** Solana Foundation, Stellar and OpenZeppelin
      skills and ToB security plugins per pack, in project scope; descriptions routed so the agent
      picks the right one; versions checked against the toolchain.
- [ ] **P2 · Isolation for higher autonomy.** ToB-style devcontainer when an agent runs with fewer
      prompts (fuzz campaigns, long audits).
- [ ] **P3 · Production operations.** Monitoring and alerts (OpenZeppelin Monitor, Tenderly or
      Forta), bug bounty (Immunefi), `SECURITY.md`, incident runbooks with pause procedures.
- [ ] **P3 · Regulation.** MiCA (EU, relevant from Portugal) and travel-rule obligations for
      products touching custody or payments.
- [ ] **Validate it like the worker:** one real small project per pack (for example an escrow or an
      ERC-4626 vault on EVM) through grill → spec → tickets → implement → review, with error and
      ambiguity scenarios, before calling the pack ready.
